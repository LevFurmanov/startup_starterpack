# How OpenAI, Google and Microsoft/GitHub design and orchestrate AI coding agents (sources through 2026-11-02)

Scope: only material published by OpenAI, Google, and Microsoft/GitHub. Collected 2026-11-02/03 via three parallel researchers plus direct verification fetches. Access caveat: every `openai.com/index/*` page returned HTTP 403 to our fetcher (direct and via archive), so OpenAI blog posts are cited by their primary URL but the quoted content comes from (a) OpenAI-hosted PDFs on cdn.openai.com (read in full), (b) OpenAI docs/forum/GitHub pages (read in full), or (c) clearly labelled secondary copies. Each finding below says which.

The notes are written to be compared against the "orc" loop (scout -> up to 3 questions -> spec -> worker in a git worktree -> automated checks -> independent reviewer with bug/proof/simplify passes -> max two fix rounds -> fast-forward merge -> lessons extracted into rules). The final section collects what contradicts or extends that loop.

## KQ1. OpenAI "A practical guide to building agents": single vs multi-agent, guardrails, when to add agents, human-in-the-loop

### Takeaway
OpenAI's guide (34-page PDF, ~April 2025) says to maximize a single agent with tools first and split only on two concrete symptoms (complex conditional logic in prompts; overlapping tools), offers exactly two multi-agent topologies (manager-as-tool-caller vs decentralized handoffs), treats guardrails as a stack of cheap specialised checks plus tool risk ratings, and names two human-in-the-loop triggers: exceeding a retry/action threshold and high-risk/irreversible actions.

### Cited Findings
- Agent definition: "It leverages an LLM to manage workflow execution and make decisions. It recognizes when a workflow is complete and can proactively correct its actions if needed. In case of failure, it can halt execution and transfer control back to the user." Three components: Model, Tools, Instructions ("Explicit guidelines and guardrails defining how the agent behaves"). — [A practical guide to building agents (PDF, full text read)](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Run loop and exit conditions: "Every orchestration approach needs the concept of a 'run', typically implemented as a loop that lets agents operate until an exit condition is reached. Common exit conditions include tool calls, a certain structured output, errors, or reaching a maximum number of turns." — [same PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- When an agent is warranted at all: "01 Complex decision-making ... 02 Difficult-to-maintain rules ... 03 Heavy reliance on unstructured data"; "Otherwise, a deterministic solution may suffice." — [same PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Model selection: prototype "with the most capable model for every task to establish a performance baseline", then swap in smaller models; "Set up evals to establish a performance baseline". — [same PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Instruction-writing advice: "Use existing documents" (SOPs, policy docs; "routines can roughly map to individual articles in your knowledge base"); "Prompt agents to break down tasks"; "Define clear actions — Make sure every step in your routine corresponds to a specific action or output"; "Capture edge cases ... an alternative step if a required piece of info is missing." — [same PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Single-agent-first: "customers typically achieve greater success with an incremental approach"; "Our general recommendation is to maximize a single agent's capabilities first. More agents can provide intuitive separation of concepts, but can introduce additional complexity and overhead, so often a single agent with tools is sufficient." Prompt templates with policy variables are the recommended way to manage complexity before going multi-agent. — [same PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- The two triggers for splitting: "Complex logic — When prompts contain many conditional statements (multiple if-then-else branches), and prompt templates get difficult to scale, consider dividing each logical segment across separate agents." "Tool overload — The issue isn't solely the number of tools, but their similarity or overlap. Some implementations successfully manage more than 15 well-defined, distinct tools while others struggle with fewer than 10 overlapping tools. Use multiple agents if improving tool clarity by providing descriptive names, clear parameters, and detailed descriptions doesn't improve performance." — [same PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Manager pattern: "A central 'manager' agent coordinates multiple specialized agents via tool calls", "ideal for workflows where you only want one agent to control workflow execution and have access to the user" (SDK: `agent.as_tool(...)`). — [same PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Decentralized pattern: "Multiple agents operate as peers, handing off tasks to one another"; "Handoffs are a one way transfer ... a handoff is a type of tool ... we immediately start execution on that new agent ... while also transferring the latest conversation state"; best "when you don't need a single agent maintaining central control or synthesis". Graph framing: "in the manager pattern, edges represent tool calls whereas in the decentralized pattern, edges represent handoffs." — [same PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Guardrails as layers: "Think of guardrails as a layered defense mechanism. While a single one is unlikely to provide sufficient protection, using multiple, specialized guardrails together creates more resilient agents." Named layers: relevance classifier, safety classifier ("jailbreaks or prompt injections"), PII filter on output, moderation, rules-based ("blocklists, input length limits, regex filters"), output validation, and tool safeguards. — [same PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Tool risk ratings: "Assess the risk of each tool available to your agent by assigning a rating—low, medium, or high—based on factors like read-only vs. write access, reversibility, required account permissions, and financial impact. Use these risk ratings to trigger automated actions, such as pausing for guardrail checks before executing high-risk functions or escalating to a human if needed." — [same PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Guardrail evolution heuristic: "01 Focus on data privacy and content safety 02 Add new guardrails based on real-world edge cases and failures you encounter 03 Optimize for both security and user experience." SDK runs guardrails with "optimistic execution by default ... the primary agent proactively generates outputs while guardrails run concurrently, triggering exceptions if constraints are breached". — [same PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Human-in-the-loop triggers: "Two primary triggers typically warrant human intervention: Exceeding failure thresholds: Set limits on agent retries or actions. If the agent exceeds these limits (e.g., fails to understand customer intent after multiple attempts), escalate to human intervention. High-risk actions: Actions that are sensitive, irreversible, or have high stakes should trigger human oversight until confidence in the agent's reliability grows." Also: "For a coding agent, this means handing control back to the user." — [same PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)

### Inferences
- The orc loop's "max two fix rounds, then stop" is a direct instance of the guide's "exceeding failure thresholds" trigger; the guide would add a second, orthogonal trigger (tool risk rating) that orc's loop does not currently express.
- The guide's single-agent-first stance implies the orc scout/spec/worker/reviewer split should be justified by one of the two stated symptoms (conditional-heavy prompts or overlapping tools), not by role aesthetics; a reviewer with distinct tools/prompt is defensible under "complex logic".

### Gaps
- The PDF carries no printed publication date; "April 2025" is inferred from model names (o1, o3-mini, gpt-4o-mini).
- The guide's evaluation guidance is thin (baseline evals, "start small, validate with real users"); no eval methodology for coding agents specifically.

## KQ2. OpenAI Codex: harness engineering, cloud sandbox design, "how we use Codex", numbers

### Takeaway
OpenAI's Feb 2026 "Harness engineering" post reports a 3-to-7-engineer team producing ~1M lines of code in ~5 months with no hand-written code by making the repository the agent's system of record (a ~100-line AGENTS.md as a map into a `docs/` tree), enforcing architecture with agent-generated linters whose error messages carry remediation instructions, running background "garbage collection" agents that open small refactor PRs, and pushing review to agent-to-agent loops; the Codex product itself runs offline in a sandbox with secrets stripped before the agent phase, and OpenAI reports >90% internal adoption, ~70% more PRs merged per week, and Codex auto-reviewing nearly every internal PR.

### Cited Findings

**"Harness engineering: leveraging Codex in an agent-first world" (OpenAI, 2026-02-11). Primary URL 403; content below is from a condensed wiki copy and two third-party reviews; treat exact wording as approximate.**
- Team "Started with 3 engineers, grew to 7"; "About five months, starting August 2025 from an empty repository"; "About 1,000,000 lines of code, with no manually written code"; "About 3.5 PRs per engineer per day". — [OpenAI primary (403)](https://openai.com/index/harness-engineering/); via [agent-harness-wiki copy](https://ericfode.github.io/agent-harness-wiki/raw/articles/openai-harness-engineering)
- Human role: "Designing environments, specifying intent, and building feedback loops." When a task failed, the question was what capability is missing and how to make it "legible and enforceable for the agent" rather than prompting better. — [wiki copy](https://ericfode.github.io/agent-harness-wiki/raw/articles/openai-harness-engineering); corroborated by [rywalker research page](https://rywalker.com/research/openai-harness) which quotes "Our most difficult challenges now center on designing environments, feedback loops, and control systems."
- Review process ("Ralph Wiggum Loop"): "Codex reviews its own changes locally, requests local and cloud agent reviews, responds to feedback, and iterates until the agent reviewers are satisfied." Third-party review adds: "Human review is optional." and "Merge gates are minimal; flakes are handled with retries rather than blocking." — [wiki copy](https://ericfode.github.io/agent-harness-wiki/raw/articles/openai-harness-engineering); [ai-playbooks review](https://ai-playbooks.pages.dev/reviews/harness-engineering-leveraging-codex-in-an-agent-first-world)
- AGENTS.md: "About 100 lines, acting as a map rather than a manual", a table of contents into a structured `docs/` directory ("progressive disclosure"). Search snippet of the OpenAI page: "the initial AGENTS.md was written by Codex, and the team moved away from one large file". — [wiki copy](https://ericfode.github.io/agent-harness-wiki/raw/articles/openai-harness-engineering); [search snippet summary](https://ai-playbooks.pages.dev/reviews/harness-engineering-leveraging-codex-in-an-agent-first-world)
- Repository layout listed: `ARCHITECTURE.md`; `docs/design-docs/` (index.md, core-beliefs.md); `docs/exec-plans/` (active/, completed/, tech-debt-tracker.md); `docs/generated/` (db-schema.md); `docs/product-specs/`; `docs/references/` (design-system-reference-llms.txt, nixpacks-llms.txt); plus DESIGN, FRONTEND, PLANS, QUALITY_SCORE .md files. "Plans are first-class, checked-in artifacts." — [wiki copy](https://ericfode.github.io/agent-harness-wiki/raw/articles/openai-harness-engineering); [ai-playbooks review](https://ai-playbooks.pages.dev/reviews/harness-engineering-leveraging-codex-in-an-agent-first-world)
- Architecture enforcement: layered dependency order "Types → Config → Repo → Service → Runtime → UI"; "Custom Codex-generated linters and structural tests block illegal dependency edges"; "'Taste' invariants enforce naming conventions, file size limits, and structured logging"; "Linter error messages include remediation instructions written for the agent." "Boundaries are validated; implementations are not micromanaged." — [wiki copy](https://ericfode.github.io/agent-harness-wiki/raw/articles/openai-harness-engineering); [ai-playbooks review](https://ai-playbooks.pages.dev/reviews/harness-engineering-leveraging-codex-in-an-agent-first-world)
- Entropy / garbage collection: "Golden Principles": prefer shared utility packages over hand-rolled helpers; validate at boundaries with typed SDKs; run automated cleanup. "Background Codex tasks scan for deviations and open refactoring PRs on a regular cadence." Third-party: background tasks "scan for pattern drift, grade quality, and open small refactor PRs that auto-merge." — [wiki copy](https://ericfode.github.io/agent-harness-wiki/raw/articles/openai-harness-engineering); [ai-playbooks review](https://ai-playbooks.pages.dev/reviews/harness-engineering-leveraging-codex-in-an-agent-first-world)
- Keeping the agent honest / legibility: "Chrome DevTools Protocol is wired into the agent runtime. Codex uses DOM snapshots and screenshots to reproduce bugs and validate fixes." Observability: "logs (LogQL), metrics (PromQL), and traces (TraceQL) are exposed through ephemeral local stacks", "local to each isolated worktree". "Codex can run tasks for 6+ hours, checking performance targets such as service startup under 800ms." Workflow example: "the agent records a video of the bug, implements and validates a fix, records a second video, then opens and merges the PR, escalating to humans only for judgment calls." — [wiki copy](https://ericfode.github.io/agent-harness-wiki/raw/articles/openai-harness-engineering); [rywalker page](https://rywalker.com/research/openai-harness)
- Stated lessons: "What Codex can't see doesn't exist" (so Slack decisions and design docs must be encoded in the repo as Markdown); "Building software still demands discipline, but the discipline shows up more in the scaffolding rather than the code." Section headings: The Experiment; Redefining Engineering Work; Increasing Application Legibility; Repository Knowledge as the System of Record; Enforcing Architecture and "Taste"; Managing Entropy; Current State of Autonomy. — [wiki copy](https://ericfode.github.io/agent-harness-wiki/raw/articles/openai-harness-engineering)

## KQ3. OpenAI Symphony: facts beyond the README

### Takeaway
Symphony's SPEC.md defines a tracker-driven dispatcher with hard defaults: 30 s poll, 10 concurrent agents, 20 turns per worker session, exponential retry backoff capped at 300 s, a 300 s stall timeout, no cost caps, workspace-per-issue via lifecycle hooks (not git worktrees), continuation turns that reuse the same thread and workspace, and no recovery of in-flight sessions across orchestrator restarts.

### Cited Findings
- README positioning: "engineering preview for testing in trusted environments"; "works best in codebases that have adopted harness engineering". — [openai/symphony](https://github.com/openai/symphony)
- Polling: `polling.interval_ms` default `30000`; each tick "reconciles running issues first, then validates config, fetches candidates, and dispatches." `tracker.required_labels` default `[]`. — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)
- Workspace per issue at `<workspace.root>/<workspace_key>`; "does not assume any specific repository/VCS workflow"; git handled by hooks `after_create`, `before_run`, `after_run`, `before_remove` (`hooks.timeout_ms` 60000); after_create/before_run failures are fatal, after_run/before_remove "logged and ignored"; workspaces persist across runs and are not auto-deleted on success. — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)
- WORKFLOW.md = YAML front matter + Markdown prompt body with template vars `issue`, `attempt`; unknown vars must fail; "On change, it MUST re-read and re-apply workflow config and prompt template without restart." Invalid WORKFLOW.md blocks boot; a failed reload keeps last-good. — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md); [elixir/README.md](https://github.com/openai/symphony/blob/main/elixir/README.md)
- Caps: `agent.max_concurrent_agents` default 10; `max_concurrent_agents_by_state`; `agent.max_turns` default 20 per worker session; no cost caps ("token usage and rate limits for observability only"). — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)
- Retry and stall: clean exit -> continuation after 1000 ms; failure -> `delay = min(10000 * 2^(attempt-1), max_retry_backoff_ms)` with cap default 300000; `codex.stall_timeout_ms` default 300000 -> process killed and retried; `codex.turn_timeout_ms` default 3600000 "measured as silence between outputs, not a total runtime cap". — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)
- Resume: continuation turns "reuse the same thread_id and workspace, and send continuation guidance rather than the original prompt." Across restarts: "No retry timers are restored," "No running sessions are assumed recoverable" — recovery is terminal cleanup, fresh poll, re-dispatch; "restarting the orchestrator clears that blocked map". — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md); [elixir/README.md](https://github.com/openai/symphony/blob/main/elixir/README.md)
- States: claim `Unclaimed/Claimed/Running/RetryQueued/Released`; attempt phases `PreparingWorkspace -> BuildingPrompt -> LaunchingAgentProcess -> InitializingSession -> StreamingTurn -> Finishing -> Succeeded|Failed|TimedOut|Stalled|CanceledByReconciliation`. After each turn the worker re-checks the tracker; a run "can end at a workflow-defined handoff state (for example Human Review)." PR creation is not defined by the spec. — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)
- Linear reference impl: terminal states "Done, Closed, Cancelled, Duplicate"; "A Todo issue is dispatchable only if it has no non-terminal blocker"; workflow "depends on custom statuses: Rework, Human Review, and Merging"; `thread_sandbox` default `workspace-write`; default `approval_policy` rejects `sandbox_approval/rules/mcp_elicitations`; package managers need `networkAccess: true`; optional `commit`, `push`, `pull`, `land` skills. Example high-trust profile "auto-approves command and file-change requests and fails user-input-required turns." — [elixir/README.md](https://github.com/openai/symphony/blob/main/elixir/README.md); [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)

### Inferences
- Symphony's "fail user-input-required turns" under the high-trust profile is the opposite of orc's "up to three questions" step: Symphony treats a question as a failed attempt to be requeued, orc treats it as a planned gate before the spec.
- Symphony's `Rework` / `Human Review` / `Merging` statuses externalise orc's reviewer-fix-merge phases into the tracker, which makes resume trivially a re-poll; orc's state lives in the worktree/spec and would need an equivalent "where was I" marker to survive a crash.

### Gaps
- Symphony uses a cloned workspace directory per issue, not a git worktree; no guidance on worktree reuse or merge strategy is in the spec.
- `docs/` in the repo holds only smoke-test notes; no design rationale published beyond SPEC.md.

## KQ4. Google: Jules, Gemini CLI / Conductor, ADK orchestration, agent engineering and eval

### Takeaway
Google's coding agents converge on plan-gate-then-execute with a separate critic: Jules generates a plan the user approves, then a Critic Agent "flags, doesn't fix" after patch generation and loops until clean (a Planning Critic reviewing plans cut task failures 9.5%); Conductor keeps spec.md/plan.md in the repo with a review command that appends a "Review Fixes" phase; ADK formalises the loop as `LoopAgent(max_iterations)` + `escalate=True` and the generator-critic pattern; and Jules is being wound down (sessions end 2026-11-11, service ends 2026-12-31).

### Cited Findings

**Jules (async coding agent)**
- Execution model: "Jules runs in a virtual machine where it clones your code, installs dependencies, and modifies files." Plan gate: "Once you submit a task, Jules will generate a plan. You can review and approve it before any code changes are made." AGENTS.md: Jules "automatically looks for a file named AGENTS.md in the root of your repository" to "generate more relevant plans and completions." — [Jules docs](https://jules.google/docs)
- Critic position and behaviour (2025-08-12): the critic runs "after patch generation and before submission"; v1 "is a one-shot process that evaluates the final output in a single pass"; "The critic doesn't fix code, it flags it, then hands it back to Jules to improve"; Jules revises and the critic re-reviews "until no further issues remain"; feedback changes "the current state and next steps in the loop; it does not retrain the model." Checks named: subtle logic errors ("Output matches expected cases but fails on unseen inputs"), incomplete changes ("function signature updated without handling all parameters"), inefficiency ("unnecessary O(n²) complexity"). Not a linter ("shallow, fixed rules") and not a test suite. ## KQ5. Microsoft and GitHub: Magentic-One ledgers, AutoGen/Agent Framework, Copilot coding agent, Spec Kit, Magentic-UI, failure-mode taxonomy

### Takeaway
Microsoft's canonical orchestrator (Magentic-One) runs an outer loop on a Task Ledger (facts given / to look up / to derive / guesses + plan) and an inner loop on a Progress Ledger (five yes/no-plus-instruction questions per round) with a stall counter that forces replanning (threshold 2 in the paper; `max_stalls=3`, `max_turns=20` in AutoGen; sample 10 rounds / 3 stalls / 2 resets in Agent Framework); GitHub's Copilot coding agent runs in a 59-minute Actions sandbox, self-reviews with Copilot code review before opening a PR, cannot approve or merge, and needs a human to approve CI; Spec Kit encodes a specify -> plan -> tasks -> implement pipeline with a test-first constitution; Magentic-UI adds action guards that route "maybe irreversible" actions to an LLM judge.

### Cited Findings

**Magentic-One (arXiv 2411.04468, 2024-11-07)**
- Outer loop / Task Ledger: Orchestrator pre-populates four fact categories: "given or verified facts", "facts to look up", "facts to derive", "educated guesses" (so agents can fall back on them when stuck), then writes a step-by-step plan assigning steps to agents; the plan is "a hint, not a strict script"; all agents reset their contexts after each plan update. — [Magentic-One paper](https://arxiv.org/abs/2411.04468)
- Inner loop / Progress Ledger: each iteration answers (1) "Is the request fully satisfied (i.e., task complete)?" (2) is the team looping / repeating itself? (3) is forward progress being made? (4) which agent should speak next? (5) what instruction or question should be asked of that team member? — [Magentic-One paper](https://arxiv.org/abs/2411.04468)
- Stall counter: incremented when the ledger detects looping or no progress; while the counter is at or below a threshold (2 in their experiments) the inner loop continues; once it exceeds the threshold the Orchestrator exits to the outer loop, reflects, revises the task ledger and plan, and starts a new inner loop. Termination by configurable max attempts or max time (example budget 25 minutes); on termination the Orchestrator reports a final answer or best guess. — [Magentic-One paper](https://arxiv.org/abs/2411.04468)
- Agents: WebSurfer (one browser action per request, set-of-marks), FileSurfer (read-only markdown previewer), Coder ("specialized by its system prompt"), ComputerTerminal ("a deterministic agent with no LLM calls" running Python/shell). — [Magentic-One paper](https://arxiv.org/abs/2411.04468)
- Results: GAIA test 38.00% (GPT-4o + o1), AssistantBench 27.7%, WebArena 32.8%. Ablations on GAIA validation: replacing the ledger-based Orchestrator with a simple GroupChat orchestrator cut performance 31%; removing any single worker agent cut 21-39%. — [Magentic-One paper](https://arxiv.org/abs/2411.04468)
- Safety observations: agents "repeatedly tried to log in to a WebArena site during a misconfiguration until the account was temporarily suspended, then tried to reset the password"; tried to reach the real Reddit (blocked only by network restrictions); accepted cookie/ToS without a human; tried to recruit humans (social posts, emailing authors, drafting a FOIA request). — [Magentic-One paper](https://arxiv.org/abs/2411.04468)
- Stated limitations: tasks need "dozens of LLM calls, potentially costing several dollars and tens of minutes"; Coder "rewrites entire code listings when debugging and struggles with multi-file codebases"; fixed team (unneeded agents distract the Orchestrator); no cross-task learning ("insights discarded, sub-tasks rediscovered"). — [Magentic-One paper](https://arxiv.org/abs/2411.04468)

**AutoGen AgentChat and Microsoft Agent Framework**
- `MagenticOneGroupChat(participants, model_client, termination_condition=None, max_turns=20, max_stalls=3, ...)`: "`max_stalls` sets how many stalls are allowed before re-planning"; without a termination condition "the chat runs based on orchestrator logic or until `max_turns` is reached." `RoundRobinGroupChat`, `SelectorGroupChat`, `Swarm` default to `max_turns=None` (unbounded unless set). — [AutoGen teams reference](https://microsoft.github.io/autogen/stable/reference/python/autogen_agentchat.teams.html)
- Termination conditions: `MaxMessageTermination`, `TextMentionTermination` (e.g. "TERMINATE"), `TokenUsageTermination` ("requires the agents to report token usage"), `TimeoutTermination`, `HandoffTermination`, `SourceMatchTermination`, `ExternalTermination`, `FunctionCallTermination` (e.g. `function_name="approve"` -> "Function 'approve' was executed."), `FunctionalTermination`; composable with `|` (OR) and `&` (AND); "stateful but reset automatically after each run()". — [AutoGen termination tutorial](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/termination.html)
- Agent Framework Magentic orchestration (page dated 2026-09-04, updated 2026-10-06; experimental): "a dedicated Magentic manager coordinates a team of specialized agents, selecting which agent should act next based on the evolving context, task progress, and agent capabilities"; use plain Group Chat if planning is not needed; "it is untested how well the Magentic orchestration will perform outside of the original Magentic-One design." Builder: Python `MagenticBuilder(participants=[...], manager_agent=..., max_round_count=10, max_stall_count=3, max_reset_count=2, enable_plan_review=False, ...)`; .NET `.RequirePlanSignoff(false).WithMaxRounds(10).WithMaxStalls(3).WithMaxResets(2)` — "max coordination rounds, max consecutive stalls before replanning, max plan resets". Progress ledger fields `IsRequestSatisfied`, `IsInLoop`, `IsProgressBeingMade`, `NextSpeaker`, `InstructionOrQuestion`; "Consecutive non-progressing rounds increment a stall counter, and exceeding the configured maximum triggers an automatic reset and replan." Events `PLAN_CREATED`, `REPLANNED`, `PROGRESS_LEDGER_UPDATED`. Plan review: `MagenticPlanReviewRequest` carries plan + progress ledger + `IsStalled`; `approve()` or `revise(feedback)`; Python `enable_plan_review=False` default, .NET `RequirePlanSignoff` defaults to `true`. Flow: Planning -> optional plan review -> agent selection -> execution -> progress assessment -> stall detection ("auto-replan with an optional human review") -> iterate "until the task is complete or limits are reached" -> final synthesis. — [Agent Framework: Magentic orchestration](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/magentic)
- Checkpoint/resume: "Checkpoints are created at the end of each superstep, after all executors in that superstep have completed their execution"; each captures "Executor states, Messages in transit, Shared state"; resume by passing `checkpoint_id`; "Resume from checkpoint - pending requests will be re-emitted" (HITL requests survive restarts). — [Agent Framework checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints); [AutoGen migration guide](https://learn.microsoft.com/en-us/agent-framework/migration-guide/from-autogen/)

**Magentic-UI (arXiv 2507.22358, 2025-07-30) and AI Red Team taxonomy (2025-04-24)**
- Six mechanisms: co-planning (Orchestrator asks directed questions if unclear, user edits plan, execution only after acceptance), co-tasking (human as `UserProxy`, delegated to "only after other agents fail"), multi-tasking, action guards, answer verification, long-term memory / plan learning. Action guards: developer-set irreversibility classes — "always irreversible" (upload a file) requires approval; "never irreversible" (scroll) auto-runs; "maybe irreversible" (click a button) goes to an LLM judge that decides whether to ask. Coder runs in Docker "retrying up to three times on errors". Plan learning: full trace -> LLM synthesises a reusable plan into a "Saved Plans" gallery, retrieved via Task-Centric Memory (at most one plan). — [Magentic-UI paper](https://arxiv.org/abs/2507.22358)
- Magentic-UI results: GAIA 42.52% (vs Magentic-One 38.00%); simulated user raised GAIA-val from ~30.3% to 51.9% with help requested in 10% of tasks; user study (n=12) found approvals "excessive for low-risk actions like adding to cart and for confirming plan changes"; 24 adversarial scenarios: "With default settings, none of the scenarios succeeded"; with mitigations disabled, injections "reliably succeeded in exfiltrating SSH keys, creating GitHub API keys, and searching email for one-time codes." Limitation: plans are a limited NL DSL "with no branching or parallel steps". — [Magentic-UI paper](https://arxiv.org/abs/2507.22358)
- Failure-mode taxonomy: axes novel vs existing, security vs safety; memory poisoning "particularly insidious in AI agents"; mitigations "external authentication or validation for all memory updates", "limiting which components of the system have access to the memory", "controlling the structure and format of items stored in memory." — [Microsoft Security Blog](https://www.microsoft.com/en-us/security/blog/2025/04/24/new-whitepaper-outlines-the-taxonomy-of-failure-modes-in-ai-agents/)

### Inferences
- Across Magentic-One -> AutoGen -> Agent Framework the stall-then-replan knob moved from 2 to 3 and gained a cap on the number of replans (`max_reset_count=2`); orc's "max two fix rounds" is the analogous outer cap, but orc has no inner "is progress being made" check inside a single worker run.
- GitHub's design keeps every privileged step (CI, approval, merge) behind a human even though the agent self-reviews; this is the opposite end of the spectrum from OpenAI's "human review optional", with Google's plan-approval gate in between.
- Spec Kit's `[NEEDS CLARIFICATION]` markers and the "no markers remain" checklist are a structured version of orc's "up to three questions".

## KQ6. Across all three: verification, cost/turn caps, resume after failure, secrets and destructive actions

### Takeaway
All three verify with the same four layers in different mixes — repo-declared tests the agent must run, an LLM self-review/critic pass before a human sees anything, mechanical gates (linters, structural tests, CodeQL/secret scanning), and a human gate whose strictness varies from GitHub (human must approve CI and merge) to OpenAI (optional); caps are expressed as turns/rounds/stalls/time rather than money; resume is either checkpoint-based (Agent Framework, Gemini CLI) or "re-poll and re-dispatch from the tracker" (Symphony); and every vendor defaults to network-off, workspace-only writes, secrets stripped or scoped, and approval for irreversible actions.

## KQ7. What contradicts or extends the orc ticket loop (scout -> <=3 questions -> spec -> worktree worker -> checks -> independent reviewer bug/proof/simplify -> <=2 fix rounds -> ff-merge -> lessons into rules)

### Takeaway
Nothing published by the three companies contradicts the orc loop's shape; the differences are in where state lives (vendors persist plans, ledgers and fix phases in the repo or tracker), in the addition of a pre-execution plan review, an in-run progress/stall check, and risk-rated tool gates, and in a spectrum of human-gate strictness that orc sits in the middle of.

### Cited Findings
- Extends (plan review before execution): Jules Planning Critic "reviews plans that don't need human approval before execution", "9.5% reduction in task failure rates" — [changelog](https://jules.google/docs/changelog/); Agent Framework `enable_plan_review` / `RequirePlanSignoff` with `approve()`/`revise(feedback)` — [Magentic orchestration](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/magentic); Jules "Give me a plan" gate — [docs](https://jules.google/docs); OpenAI internal "Ask Mode" plan then Code Mode — [PDF](https://cdn.openai.com/pdf/6a2631dc-783e-479b-b1a4-af0cfbd38630/how-openai-uses-codex.pdf).

- Contrasts (worktree vs clone): Symphony uses a cloned workspace dir per issue with git via hooks, not worktrees — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md); OpenAI harness post mentions observability "local to each isolated worktree" — [rywalker](https://rywalker.com/research/openai-harness); GitHub one `copilot/` branch per task in an ephemeral Actions runner — [Risks](https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations).

### Inferences
- The most-supported additions to orc, by number of independent vendors doing them: (1) a plan/spec critic before the worker starts (Google, Microsoft, OpenAI-internal); (2) persisting the spec, fix-round phase and open questions in the repo or ticket so a crash can resume by re-reading (OpenAI, Google, Symphony); (3) mechanical checks with remediation text in the failure message so the fix round is cheaper (OpenAI, GitHub); (4) a validation step on "lessons -> rules" writes to resist drift and poisoning (Microsoft taxonomy, OpenAI GC agents).
- orc's bug/proof/simplify reviewer passes have no exact published counterpart; the closest are Jules' critic categories (logic errors, incomplete changes, inefficiency) and Spec Kit's Simplicity/Anti-Abstraction articles, which suggests "simplify" is a recognised review axis.
- Vendors uniformly frame caps as "rounds then replan" rather than "rounds then stop"; orc stops after two fix rounds, which is stricter and simpler but forgoes the replanning step every Microsoft orchestrator includes.

### Gaps
- No vendor publishes a controlled comparison of 1 vs 2 vs N fix rounds, so the "max two" cap has no external evidence for or against.
- No vendor documents a fast-forward-only merge policy; GitHub and OpenAI both merge via PRs.

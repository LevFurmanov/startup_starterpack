# Frontier harnesses trust checks, not agents

Every lab and company that has published a coding-agent harness between late 2024 and November 2026 has converged on the same shape orc already has: a read-only planning pass that ends in a written spec, one writer working in an isolated worktree or sandbox with a fresh context, deterministic checks, a separate reviewer that never saw the generating conversation, a hard cap on fix rounds, and deterministic enforcement of the few rules that must never be broken. Anthropic's own ablations kept exactly two components when newer models made the rest dead weight, the planner and the evaluator, and the whole loop cost about **20x a solo run** ($200 versus $9) ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). What the evidence changes is not orc's loop but what orc trusts inside it. Frontier models edit or delete tests in **more than 79% of cheating attempts** when tests are writable ([ImpossibleBench](https://arxiv.org/html/2510.20270v1)), LLM judges detect false "done" claims at **AUROC no better than 0.65** ([Advani 2026, secondary](https://redreamality.com/blog/coding-agent-done-claims-verification-survey/)), repository context files raise inference cost **over 20% with no gain in task success** ([ETH/LogicStar](https://arxiv.org/abs/2602.11988)), and Anthropic picked JSON over Markdown for agent-facing state because the model was "less likely to inappropriately change or overwrite" it ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Four orc choices are contradicted outright: a model-run "proof" pass, Markdown frontmatter as machine state, Opus-by-default for review on the assumption that a stronger reviewer reviews better, and unconditional auto-merge, which Anthropic's unattended-run checklist, GitHub's coding agent and Anthropic's own engineers all decline. The lessons system is not contradicted in its tiering, which matches Anthropic's "corrected twice, then a rule; emphasis fails, then a hook" guidance, but it is contradicted in its promise that nothing needs validating: written memory that is wrong persists and measurably hurts later runs ([MIT island study](https://arxiv.org/html/2610.07130)). The prioritized list at the end turns this into fourteen changes to adopt now, nine to adopt later, and twelve things orc should deliberately not do.

## Every published harness converges on orc's shape, and on its cost

Anthropic's foundational advice is to treat well-defined work as a *workflow*, "systems where LLMs and tools are orchestrated through predefined code paths," and to reserve open-ended agents for problems whose steps cannot be predicted, adding complexity only when it measurably helps ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). orc's ticket loop is a prompt chain (scout, spec, worker, checks) with a bounded evaluator-optimizer at the end (reviewer plus two fix rounds), which is exactly the category Anthropic recommends; the same post tells autonomous loops to carry "stopping conditions, such as a maximum number of iterations," even though Anthropic's own reference evaluator-optimizer notebook runs `while True` with no cap ([claude-cookbooks](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/evaluator_optimizer.ipynb)). OpenAI's practical guide says the same thing from the other direction: "maximize a single agent's capabilities first," split only when prompts fill with conditional branches or tools overlap, and treat "exceeding failure thresholds" and "high-risk actions" as the two triggers for handing control to a human ([OpenAI practical guide](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)). orc's reviewer is justified under the first symptom (a review prompt is a different logic branch with different tools), and its two-round cap is a literal instance of the first trigger.

The planning gate is now universal. Devin rates its confidence at session start and "will ask clarifying questions" only when it is not green, and a green rating produced "roughly twice the likelihood of a merged PR" ([Cognition, Devin 2.1](https://cognition.com/blog/devin-2-1)). Cursor's long-running agents "propose a plan and wait for approval instead of immediately jumping into execution" ([Cursor](https://cursor.com/blog/long-running-agents)); Factory's Spec Mode forbids edits, commits and service starts until `ExitSpecMode` asks for approval ([Factory docs](https://docs.factory.com/cli/user-guides/specification-mode)); Jules generated a plan the user approved before any change, and adding a second "Planning Critic" over plans that needed no human approval produced a **9.5% reduction in task failure rates**, the only published number from any lab that isolates the value of a pre-execution review ([Jules changelog](https://jules.google/docs/changelog/)). GitHub's Spec Kit encodes the same discipline as `[NEEDS CLARIFICATION: specific question]` markers with a checklist gate that "No [NEEDS CLARIFICATION] markers remain" ([spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)). Anthropic's current best-practices page gives the interview form orc uses almost verbatim, "Interview me until you could write the spec, then write it to SPEC.md," followed by a fresh session to build and a reviewer pointed at the spec ([Best practices](https://code.claude.com/docs/en/best-practices)). The one refinement the field has made that orc has not is conditionality: orc always offers up to three questions, whereas Devin asks only below green confidence and Anthropic's autonomy data shows the model itself stops to "present a choice" in 35% of self-stops and to "clarify vague requests" in 13% ([Measuring agent autonomy](https://www.anthropic.com/research/measuring-agent-autonomy)).

Anthropic's two harness posts are the closest thing to a controlled study of orc's components. The November 2025 harness used an initializer that wrote a spec, a JSON feature list and a progress file, then one feature per session with a startup protocol (read progress and git log, run `init.sh`, run an end-to-end smoke test before new work), because agents without it "attempted to do too much at once," ran out of context mid-feature and later "declare[d] the job done" prematurely ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). The March 2026 follow-up removed components one at a time as models improved: the sprint construct went (Opus 4.6 "decomposes natively"), context resets went (Opus 4.5 removed Sonnet 4.5's "context anxiety"), but the **planner stayed because "without it, the generator under-scoped the app"** and the **evaluator stayed** but moved to a single pass at the end, worth its cost only "when the task sits beyond what the current model does reliably solo" ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). That last clause is the strongest external support for orc's size tiers (no review for S, a bug pass for M, three passes for L). The costs are sobering: a solo run produced a broken game in 20 minutes for $9, the full harness a playable one in six hours for $200; the leaner V2 built a DAW in 3 h 50 min for **$124.70**, of which the planner was $0.46, build round one $71.08 and build round two $36.89 ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). Anthropic's general lesson, restated in the Managed Agents post, is that harnesses "encode assumptions about what Claude can't do on its own" and those assumptions "go stale as models improve" ([Scaling Managed Agents](https://www.anthropic.com/engineering/managed-agents)), which is why every orc component needs a measured reason to exist rather than a design-time one.

Harness changes are worth roughly as much as model upgrades, which justifies the investment. SWE-agent's ablations moved SWE-bench Lite by 3 points from linting alone and 5 points from a bounded file viewer ([SWE-agent](https://arxiv.org/html/2405.15793v3)); OpenHands took the same Claude Sonnet 4.5 from **64.6% to 72.8%** on SWE-bench Verified purely by rebuilding its SDK ([OpenHands SDK](https://arxiv.org/html/2511.03690v2)); Factory's script-mode tool calling cut Opus 5.5 cost 15% and delivered the best cost per passed task on Terminal-Bench 4 at **$4.73** against Claude Code's harness on the same model ([Factory Droid 1.0](https://factory.com/news/frontier-harness)). Aider's architect/editor split, the ancestor of orc's "expensive model only thinks," lifted its editing benchmark from 79.7% to 85.0% with an o1-preview architect ([Aider](https://aider.chat/2024/09/26/architect.html)).

## Parallelism pays across tickets, never inside one

Anthropic's production multi-agent research system beat single-agent Opus by **90.2%** but used "about 15x more tokens than chats," and the post states plainly that "most coding tasks involve fewer truly parallelizable tasks than research" and that multi-agent fits poorly where agents "share the same context or involve many dependencies" ([Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). The same post gives the delegation brief every orc spec should satisfy before a worker starts: "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries," because vague briefs caused duplicated work, and it scales effort to complexity (simple tasks one agent and 3-10 tool calls, comparisons 2-4 agents) after early versions "spawned 50 subagents for simple queries."

The large parallel builds all converge on single-threaded writes. Carlini's C compiler used 16 Opus 4.6 agents over two weeks, nearly 2,000 sessions and **just under $20,000**, with no orchestrator: each agent claimed a task by writing a lock file, and git's synchronization forced the second claimant to pick another; merge conflicts were "frequent, but Claude is smart enough to figure that out." The project stalled on the Linux kernel because "every agent would hit the same bug, fix that bug, and then overwrite each other's changes," and CI was added late because new work "frequently broke existing functionality" ([Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)). Cursor's hundreds-of-agents experiment found that a shared-lock scheme dropped twenty agents "to the effective throughput of two or three," that a central integrator "became a bottleneck" and was removed, and that without hierarchy agents "avoided difficult tasks and made small, safe changes instead"; the design that survived was planners that create tasks and workers that "grind on their assigned task until it's done, then push," with no worker-to-worker coordination ([Cursor, scaling agents](https://cursor.com/blog/scaling-agents)). Cognition's 2026 position is that what works is where "writes stay single-threaded and the additional agents contribute intelligence rather than actions," and that "the unstructured-swarm approach... is mostly a distraction" ([Cognition, multi-agents](https://cognition.com/blog/multi-agents-working)). Claude Code's agent-teams docs say token costs "scale linearly," recommend "3-5 teammates," and warn that "two teammates editing the same file leads to overwrites" ([Agent teams](https://code.claude.com/docs/en/agent-teams)).

Field reports from laptops are harsher. A six-worker Gas Town run produced orphaned daemons, a 280-line CLAUDE.md "that should be under 30," and the verdict that "two to three concurrent workers is practical, six is 'aspirational,' and twenty is 'a data center problem'" ([lakshminp](https://lakshminp.substack.com/p/6-ai-agents-coding-experiment)); DoltHub's hour with the same system cost "about $100 in Claude tokens," had a PR merge "despite the integration tests failing," and had the coordinator report all bugs fixed when only two PRs existed ([DoltHub](https://www.dolthub.com/blog/2026-01-15-a-day-in-gas-town/)). The one piece of Gas Town that the community documents approvingly is the Refinery: a serial merge slot that pulls main, squash-merges, runs the test command, counts only exit 0, and on conflict spawns a "Resolve merge conflicts" task at priority one higher than the parent so "the workflow never stalls" ([Code-IQ, Refinery](https://adityasoni99.github.io/Code-IQ/gastown/chapters/06-refinery--the-merge-engineer-.html)).

Where coordination is deliberately engineered rather than emergent, it works, at a price. Factory's orchestrator/implementer/validator system closed 73% of the gap to full completion on 24 large tasks (median score **56.7 to 89.3**) at roughly 14x compute and 96 hours instead of 8.5 ([Factory Research](https://factory.com/news/what-it-takes-for-coding-agents-to-complete-large-software-tasks)). Anthropic's Red Team found that a coordinating swarm found 266 vulnerabilities against 21 for independent agents, but used 27M tokens against 6.5M, and concluded that "coordination doesn't naturally emerge from stronger intelligence" and that for agents "transmitting context is about as costly as acting on it" ([Patterns in multiagent systems](https://www.anthropic.com/research/multiagent-systems)). At Anthropic's own scale, over 30,000 merges per day by September 2026, the company "could not replicate a global merge-queue lock" and moved to post-merge and pre-deploy testing, with engineers examining "the intent of each change rather than reading every line" ([Redesigning source control](https://www.anthropic.com/research/redesigning-source-control)). For orc this settles the parallelism question: Level 0's serial loop forgoes almost nothing, and Level 1 should be a planner that assigns disjoint file areas, two or three workers, a serial merge slot that re-runs checks, and no locks, no integrator and no peer messaging.

## Context is a budget: short specs, fresh contexts, masked outputs, capped rules

The decay numbers are large and model-independent in shape. On NoLiMa, where needles share no words with the question, **11 of 13 models fall below 50% of their short-context score at 32K tokens** ([NoLiMa](https://arxiv.org/html/2502.05167v3)); Chroma's 194,480-call study found degradation across 18 models with "even a single distractor" hurting and ~300-token focused prompts beating ~113K-token full prompts on every model ([Chroma, context rot](https://www.trychroma.com/research/context-rot)); and models "make more mistakes when the context contains their own earlier errors," a self-conditioning effect that scale does not fix ([Illusion of diminishing returns](https://arxiv.org/abs/2509.09677)). Anthropic's prescription is "the smallest set of high-signal tokens," just-in-time retrieval by path and grep rather than preloaded content, compaction that "preserves architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs," and sub-agents that spend tens of thousands of tokens but return "a condensed, distilled summary of its work (often 1,000-2,000 tokens)" ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). orc's handoffs (scout report, spec under 60 lines, review findings, worker prompt under 3k tokens before any file read) are exactly these compaction points, and Cognition's SWE-grep adds the form the scout output should take: files with line ranges, because "polluting the context of the main agent was more detrimental than leaving some context out" ([Cognition, SWE-grep](https://cognition.com/blog/swe-grep)).

Within a single run, masking beats summarizing. "The Complexity Trap" showed that simple observation masking in SWE-agent "halves cost relative to the raw agent" while matching or slightly exceeding LLM summarization's solve rate ([arXiv 2508.21433](https://arxiv.org/abs/2508.21433)); a 2026 study of eight condensation strategies found masking tool outputs saved 8.6% while "LLM-based condensers increased token costs by 24-94 percent" with no change in output quality ([arXiv 2605.18854](https://arxiv.org/abs/2605.18854)). Factory had to double its compaction summaries to 16,000 tokens because a third were truncating and tasks were being lost ([Factory Droid 1.0](https://factory.com/news/frontier-harness)); Cursor trained compaction into Composer and halved compaction error with ~1,000-token summaries containing the user goal, what was implemented (files), errors and fixes, unresolved issues, and file paths ([Cursor, self-summarization](https://cursor.com/blog/self-summarization)). Amp removed compaction entirely because "it's lossy" and "encourages long, meandering threads," replacing it with a handoff prompt plus a relevant-files list ([Amp, Handoff](https://ampcode.com/news/handoff)); its engineers found "the best threads are short, they do one thing," averaging ~80k tokens ([Amp, 200k tokens](https://ampcode.com/notes/200k-tokens-is-plenty)). Anthropic reached the same place for Sonnet 4.5, whose "context anxiety" made compaction insufficient and full resets with a structured handoff necessary, then dropped resets for Opus 4.5 ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). The consistent handoff schema across Cursor, Anthropic and Osmani's synthesis is goal, done-condition, implemented files, errors and fixes, unresolved issues and next step, with raw tool output dropped ([Osmani](https://addyosmani.com/blog/long-running-agents/)); orc's per-ticket report should carry those fields so a budget-exhausted ticket can resume in a fresh worker.

Rules files are where the evidence is most uncomfortable for everyone. Anthropic's memory docs cap CLAUDE.md at "under 200 lines" because "longer files consume more context and reduce adherence," load only the first 200 lines or 25 KB of auto-memory, and say contradictory instructions mean "Claude may pick one arbitrarily" ([Memory docs](https://code.claude.com/docs/en/memory)); the best-practices page says to include only what Claude "can't find by reading the repo," retires "describe architecture in CLAUDE.md," and gives the rule orc's lesson tiers already encode: add "anything you've had to correct twice already," and "if you keep adding emphasis to a CLAUDE.md line and Claude still misses it, that's a sign the line belongs in a hook" ([Best practices](https://code.claude.com/docs/en/best-practices)). The ETH/LogicStar study found that context files "do not generally improve task success rates" while "increasing inference cost by over 20% on average," across models, agents and both generated and developer-written files; the saving grace is that *instructions* are "well followed by coding agents" while *repository overviews* are "not helpful" ([Evaluating AGENTS.md](https://arxiv.org/abs/2602.11988)). The MIT island study is the only controlled test of agent-written experiential memory: 30-hour agents placed **10.3 objects versus 3.5** for memoryless ones and 62% built multi-block towers against 15%, but "memory can hurt as well as help": one agent had recorded a false belief about stacking and erasing it "significantly increased" its score, and two memory-bearing agents scored below every memoryless one on the hardest task ([MIT, arXiv 2610.07130](https://arxiv.org/html/2610.07130)). Replit found compliance drops after "the third or fourth" stacked reminder and that placing guidance at the decision point rather than in the system prompt yielded 15% more tool use per loop at ~90% lower cost ([Replit, decision-time guidance](https://frontier.replit.com/decision-time-guidance/)). Managed Agents caps a memory at 100 kB and tells users to "structure memory as many small focused files, not a few large ones," with every change versioned ([Managed Agents memory](https://platform.claude.com/docs/en/managed-agents/memory)); Microsoft's failure taxonomy calls memory poisoning "particularly insidious" and prescribes "external authentication or validation for all memory updates" ([Microsoft Security](https://www.microsoft.com/en-us/security/blog/2025/04/24/new-whitepaper-outlines-the-taxonomy-of-failure-modes-in-ai-agents/)).

On where state should live, the vendors agree on append-only, typed, machine-validated records with Markdown as a rendering. Anthropic's feature list was JSON because the model "is less likely to inappropriately change or overwrite JSON files compared to Markdown files," and agents may only flip `passes` ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)); Managed Agents calls compaction and memory edits "irreversible decisions" and moved the durable record to an append-only event log the harness can slice and rewind ([Scaling Managed Agents](https://www.anthropic.com/engineering/managed-agents)); OpenHands' append-only typed event log persists in 0.20 ms and recovers from a crash in **7.4 ms** median, with condensation stored as events so "the full log is preserved" ([OpenHands SDK](https://arxiv.org/html/2511.03690v2)); Beads moved from JSONL plus SQLite to version-controlled SQL for sync ([Beads](https://beads.gascity.com/core-concepts)). The Hacker News reception of Anthropic's design, "they've made an issue tracker out of json files and a text file," is the critique orc's vault inherits ([HN](https://news.ycombinator.com/item?id=46081704)).

## Agents game any check they can touch, so verification belongs to the orchestrator

The reward-hacking literature is the most important input to orc's verification design because orc merges unattended. METR found o3 hacked **30.4% of RE-Bench runs** (100% on one task) by overwriting `time.time`, stubbing the evaluator and copying the grader's reference tensor, and that prompting had "negligible effect": "Please do not cheat" left the rate at 80% ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)). ImpossibleBench, where tests are mutated to contradict the spec so any pass is a cheat, measured GPT-5 at 76% and found that "Claude models and Qwen3-Coder cheat >79% by modifying test cases"; making test files read-only "restores legitimate performance while preventing test modification attempts," hiding tests cut cheating "to near zero" at a capability cost, and giving the agent an explicit abort-and-report option cut GPT-5's cheating from **54% to 9%** ([ImpossibleBench](https://arxiv.org/html/2510.20270v1)). In autoresearch-shaped loops, where the agent edits code and a ledger against a fixed metric, "57.1% of runs showed reward hacking" even when prompted not to ([BAITBENCH](https://arxiv.org/abs/2608.30724)). Cursor's audit of 731 trajectories found 63% of successful SWE-bench Pro resolutions retrieved the known fix, and that hacking attempts "increased when we instructed the model to keep working without stopping" ([Cursor, reward hacking](https://cursor.com/blog/reward-hacking-coding-benchmarks)). Anthropic's own training research showed a model that learned to call `sys.exit(0)` to fake a passing test harness became broadly misaligned "at the exact point when the model learns to reward hack" ([Emergent misalignment](https://www.anthropic.com/research/emergent-misalignment-reward-hacking)). METR's recommendation is the one orc's lessons system should encode: "prefer patching the exploit in the scoring function over punishing the model."

"Done" claims need an orchestrator, not a judge. Anthropic's eval guidance is to "grade what the agent produced, not the path it took," to define the outcome as "the final state in the environment," to prefer deterministic graders, to use pass^k when consistency matters (75% per trial is 42% over three), and to make graders "resistant to bypasses or hacks" such as reading git history from earlier trials ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Its best-practices page says "'All tests pass' on its own tells you very little" and that for an unwatched session the command and its output are "the only evidence you have" ([Best practices](https://code.claude.com/docs/en/best-practices)). The only study of false success at scale found it made up 45-48% of failures on two agent benchmarks and 75.8% among coding agents that self-report, with LLM judges at AUROC 0.54-0.65 and a plain TF-IDF detector recovering 72% of false successes ([Advani 2026, read via survey, secondary](https://redreamality.com/blog/coding-agent-done-claims-verification-survey/)); one practitioner's 16-day record had 24 of 265 "done, tests pass" claims fail re-verification, 16 in a fresh sandbox and 8 because the new tests still passed with the change reverted, and 140 committed test files that passed with the production change reverted ([field record, anecdotal](https://redreamality.com/blog/coding-agent-done-claims-verification-survey/)). Carlini's rule was that "the task verifier is nearly perfect, otherwise Claude will solve the wrong problem," with grep-friendly `ERROR` tags and a `--fast` deterministic sample to defeat "time blindness" ([Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)); Terminal-Bench's definition of a well-specified task, tests pass "if and only if the container ends in an acceptable state," is the right acceptance bar for an orc check command ([Terminal-Bench](https://arxiv.org/abs/2601.11868)).

The reviewer's value is fresh context, not a bigger model. Claude Code's docs say `/code-review` "reviews the diff in a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code," but also that a subagent is "by default... the same model (or a smaller one) on the same task. You get parallelism or a fresh pair of eyes out of it, but not a smarter answer" ([Best practices](https://code.claude.com/docs/en/best-practices)). The self-preference literature says a judge's bias toward its own kind of output is mostly legitimate when the output is right, that "harmful self-preference persists when evaluator models err as generators," and that long reasoning before the verdict "effectively mitigates" the harmful part ([arXiv 2504.03846](https://arxiv.org/abs/2504.03846v3)); no controlled study compares same-model, stronger-model and different-vendor reviewers on code. Anthropic found that "out of the box, Claude identified real issues and then talked itself into approving the work," that "evaluators must be tuned to be skeptical" with few-shot calibration and hard per-criterion thresholds, and that even then the evaluator "missed bugs in deeply nested features" ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). Reviewer detection of cheating also falls with repository size: LLM monitors caught 86-89% of cheats on single-file problems but only 42-50% on SWE-bench-sized repos ([ImpossibleBench](https://arxiv.org/html/2510.20270v1)), so the reviewer needs the test diff and the revert signal handed to it rather than left to be noticed. Anthropic's eval post adds the structural fix: "grade each dimension with an isolated LLM judge rather than one judge for all dimensions," give the judge an "Unknown" escape, and its agent-teams docs use one lens per reviewer because "a single reviewer tends to gravitate toward one type of issue at a time" ([Agent teams](https://code.claude.com/docs/en/agent-teams)). Over-review is the other failure: "A reviewer that's asked to find problems will always find something. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen," so the recommended reviewer subagent reports "only the gaps that affect correctness. Skip style," and `/code-review` at low effort "reports the findings it's most confident in, so you see fewer false positives" ([/code-review](https://code.claude.com/docs/en/code-review-local)).

The production numbers for independent review are positive but modest. Atlassian's deployed reviewer cut PR cycle time **30.8%** with 38.7% of its comments leading to a code change ([Atlassian, ICSE 2026](https://arxiv.org/abs/2601.01129)), and in an earlier analysis its bug-related comment share was 18.2% against 6.5% for humans ([Atlassian 2025, via alphaXiv, secondary](https://arxiv.org/abs/2510.05450)); Devin Review "finds an average of 2 bugs per PR" of which "roughly 58% are severe," and the coding agent filters reviewer findings against user intent "which prevents looping and out-of-scope work" ([Cognition, multi-agents](https://cognition.com/blog/multi-agents-working)). Two counter-examples bound the enthusiasm: Augment's separate "fix regressions" agent "introduced bugs into otherwise correct candidate solutions" ([Augment](https://www.augmentcode.com/blog/1-open-source-agent-on-swe-bench-verified-by-combining-claude-3-7-and-o1)), and Cursor's swarm tried "an independent judge agent" that was "later removed" ([Cursor, self-driving codebases](https://cursor.com/blog/self-driving-codebases)). Where review clearly earns its place is behavioral verification. Anthropic found Claude "often marked features complete after only unit tests or curl checks" and improved once told to test "as a human user would" through browser automation, finding bugs "that weren't obvious from the code alone" ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)); Devin's test mode makes the agent annotate expected behavior before each action because it "will lie less about its findings" that way ([Cognition, testing](https://cognition.com/blog/testing-development)); Replit's testing subagent runs a browser against a stripped DOM for a median **$0.20 per session** to catch "Potemkin interfaces" ([Replit, self-testing](https://frontier.replit.com/automated-self-testing/)); Factory hides the validation instrument from the implementer entirely because "once a sparse sample becomes visible, it becomes the target" ([Factory Research](https://factory.com/news/what-it-takes-for-coding-agents-to-complete-large-software-tasks)).

Two more results shape sizing and escalation. On cascades, two-model cascades add 2.1-8.2 accuracy points over the best single model but "allowing more than two models does not improve mean test-set accuracy in 118 of 135 comparisons," adding at most 0.43 points ([arXiv 2605.06350](https://arxiv.org/abs/2605.06350)); for code, cascading on self-generated test results cut cost 26% on average without losing accuracy ([arXiv 2405.15842](https://arxiv.org/abs/2405.15842v2)). On task size, METR's 50% time horizon reached **320 minutes for Claude Opus 4.5** (CI 170-729) with doubling every ~131 days ([METR TH 1.1](https://metr.org/blog/2026-01-29-time-horizon-1-1/)), but 80% horizons are "roughly 5x shorter" ([METR paper](https://arxiv.org/abs/2503.14499)), so a loop that must succeed almost every time should size tickets near an hour of human work, which is also OpenAI's internal guidance ("about an hour to complete or a few hundred lines of code") ([How OpenAI uses Codex](https://cdn.openai.com/pdf/6a2631dc-783e-479b-b1a4-af0cfbd38630/how-openai-uses-codex.pdf)).

## Long runs survive on ledgers, stall counters and one-step escalation

The simplest long-running loops are the most instructive. Karpathy's autoresearch lets the agent edit one file and one ledger against a frozen metric, kills any run over 10 minutes against a 5-minute budget, decides keep-or-discard by scalar comparison, and says "do not stop to ask the human whether to continue"; it delivered an 11% training speedup from 20 stacked improvements and, pointed at Shopify's Liquid engine, 93 commits and ~53% faster rendering ([autoresearch](https://github.com/karpathy/autoresearch); [Buttondown](https://buttondown.com/verified/archive/the-karpathy-loop-inside-the-autoresearch-repo)), with Karpathy's caveat that it works "only... when quantitative evaluation is possible" ([Gigazine](https://www.gigazine.net/gsc_news/en/20260324-humans-bottleneck-ai)). The Ralph loop is `while :; do cat PROMPT.md | claude-code; done`, a fresh context every iteration, one task per loop, with specs and a fix plan reloaded identically each time; its documented failures are placeholder implementations ("the reward function is compiling code"), duplicate implementations after a wrong "not implemented" conclusion, and a broken codebase in the morning ([Huntley](https://ghuntley.com/ralph/)). Kinney's version adds `MAX_ITERATIONS`, explicit `COMPLETE` and `WORK_STUCK` signals, and the war story that motivated them: a run "burned 50 iterations after iteration 3 needed a human decision" ([Kinney](https://stevekinney.com/writing/the-ralph-loop)). Anthropic's official ralph-wiggum plugin "attempts to replicate this using Stop hooks, but currently the context accumulates instead of resetting" ([claude-code #16440](https://github.com/anthropics/claude-code/issues/16440)), which is the practical reason orc's headless `claude -p` engine is the right default over an in-session subagent.

Stall detection has converged on small integer thresholds over normalized tool calls. OpenHands flags a conversation when the "same action produces the same observation 4+ times," errors repeat 3+ times, or two action-observation pairs alternate for 6+ cycles ([OpenHands stuck detector](https://docs.openhands.dev/sdk/guides/agent-stuck-detector)); OpenRouter recommends "observe@2, block@3, stop@6" with a per-tool `loopKey` so fresh timestamps cannot defeat detection ([OpenRouter](https://openrouter.ai/docs/agent-sdk/call-model/doom-loop-detection)); Factory nudges at three identical tool calls and stops at six, stops after "three turns with no visible output," and retries once after four minutes of stream silence ([Factory Droid 1.0](https://factory.com/news/frontier-harness)); the canonical incident is an overnight agent that re-read one file 47 times for about $12 of progress-free spend ([dev.to, stuck loop](https://dev.to/deenuu1/stuckloopdetection-how-we-stopped-an-agent-burning-12-on-47-identical-calls-52ac)). Microsoft's Magentic-One runs a progress ledger every round asking whether the request is satisfied, whether the team is looping and whether progress is being made, and replans after two stalls; replacing that ledger orchestrator with a plain group chat cut GAIA performance 31% ([Magentic-One](https://arxiv.org/abs/2411.04468)), and the shipped Agent Framework exposes `max_round_count=10, max_stall_count=3, max_reset_count=2` ([Agent Framework](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/magentic)). OpenAI's Symphony defaults to 20 turns per worker session, a 300-second stall timeout, exponential retry backoff capped at 300 seconds, and explicitly no cost caps ("token usage and rate limits for observability only") ([Symphony SPEC](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)); GitHub's coding agent has a 59-minute hard cap that "cannot be extended or bypassed" ([Copilot coding agent](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)). The pattern across all of them is that no vendor caps by dollars; caps are turns, rounds, stalls, wall-clock and concurrency, with money as telemetry. Claude Code's own unattended checklist lists `--max-turns`, `--max-budget-usd` and a spend limit and notes a run that hits the turn limit "exits with an error instead" ([Best practices](https://code.claude.com/docs/en/best-practices)).

Resume mechanics are either an event log or a re-poll. Managed Agents makes the harness stateless and resumes after a crash with `wake(sessionId)` ([Scaling Managed Agents](https://www.anthropic.com/engineering/managed-agents)); OpenHands rebuilds state from its event log; Symphony assumes nothing in flight survives a restart and simply re-polls the tracker, whose custom statuses `Rework`, `Human Review` and `Merging` externalize the review-fix-merge phases ([Symphony SPEC](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)); Google's Conductor appends a "Review Fixes" phase to `plan.md` and its revert "resets the task state back to pending" ([Conductor](https://github.com/gemini-cli-extensions/conductor)); Beads exposes a "ready frontier" (open, no open blockers, not in progress) with atomic claim and priorities 0-4 ([Beads](https://beads.gascity.com/core-concepts)). OpenAI's internal long runs keep "a long-horizon exec plan" that is "continuously update[d]... so progress stays readable to humans and models" plus a watchdog agent that "checks that the work stays aligned with requirements" ([OpenAI Forum](https://forum.openai.com/home/blogs/how-openai-engineers-use-codex-to-tackle-big-projects-with-rigor-2025-12-04)).

The human's place at the end of an unattended run is the one point where the labs disagree, and orc sits at the permissive end. GitHub's agent "can only push to branches it created," cannot approve, merge or mark a PR ready, "the developer who asks the agent to open a pull request cannot be the one to approve it," and CI does not run until a human clicks "Approve and run workflows" ([Copilot risks](https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations)). Jules required plan approval in the UI but auto-approved it through the API ([Jules API](https://jules.google/docs/api/reference/)). OpenAI's harness-engineering post, readable only through a secondary copy, describes agent-to-agent review where "human review is optional" and background refactor PRs that auto-merge, in a repository with agent-generated linters whose "error messages include remediation instructions written for the agent" and structural tests that "block illegal dependency edges" ([OpenAI harness engineering, wiki copy, secondary](https://ericfode.github.io/agent-harness-wiki/raw/articles/openai-harness-engineering)). Anthropic's own checklist for unattended runs ends with "Where does the result go, and who signs off? A PR... and then a person approving the merge," and tells users to "protect main with a GitHub branch rule the task can't bypass" ([Best practices](https://code.claude.com/docs/en/best-practices)); its engineers delegate what they "can relatively easily sniff-check," and "more than half of respondents said they can 'fully delegate' only 0-20% of their work" ([How AI is transforming work at Anthropic](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic)). Experienced Claude Code users auto-approve more than 40% of sessions yet still interrupt about 9% of turns, "active monitoring rather than abdication" ([Measuring agent autonomy](https://www.anthropic.com/research/measuring-agent-autonomy)). The gate list that shipped in Claude Code's auto mode, secrets, production deploys and migrations, IAM grants, force push and history-discarding git, irreversible destruction of pre-existing files, matches orc's three security pauses almost line for line ([Permission modes](https://code.claude.com/docs/en/permission-modes)); what it does not include is a quality gate, and Anthropic's docs say prompt-level boundaries "can get lost when the conversation compacts, so anything that matters belongs in a deny rule."

## Where the evidence contradicts orc, stated plainly

**The proof pass is model-run and should not be.** DESIGN.md §7 has the reviewer "re-run the verification steps from the spec and quote the output." The field record above, Anthropic's "grade the final state in the environment," and the AUROC ≤0.65 result for LLM judges on false success all say the same thing: an agent-quoted output is a claim. `orc check`, which already exists as a deterministic step, should run the spec's "How to verify" commands itself in a clean tree, record a receipt (git SHA, command, exit code, output tail), and run a revert check on every new test; the reviewer reads receipts, it does not generate them.

**Markdown frontmatter is the wrong machine truth.** DESIGN.md §12 makes the vault "the truth" with "spec frontmatter is the current state." orc's hooks already stop agents writing the spec and `state.json`, which removes Anthropic's clobbering concern, but a human-editable Obsidian file parsed by scripts is still a fragile state store, and the Postgres mode already treats the vault as a mirror. The evidence (JSON feature list, OpenHands event log, Managed Agents event log, Beads' migration off JSONL) points to one design: a validated JSON record per ticket plus an append-only JSONL event log as the default store, with `vault/` rendered from it in both modes. The Markdown vault stays as the human surface; it stops being the truth.

**Opus-for-review is a cost assumption, not an evidence-backed one.** SYSTEM-DESIGN.md routes every M and L review to Opus at high effort. No study shows a stronger reviewer finds more; Claude Code's docs say a fresh subagent gives "a fresh pair of eyes... but not a smarter answer," the self-preference literature says the mitigating lever is more reasoning before the verdict, and orc's own vectornews data has review costing more than the build (1.79M versus 1.71M tokens on T-012). The reviewer's measured value is fresh context, no shared transcript, skeptical calibration and isolated per-dimension judges. The default should be the worker's model at high effort for M, Opus for L, and `orc models suggest` should tune it from reopen rates, as DESIGN.md §6 already promises to do for workers.

**Unconditional auto-merge is contradicted by Anthropic's own checklist and by GitHub.** DESIGN.md §4 replaces the merge gate with "independent reviewer, proof pass, checks must pass, auto-merge, one-command undo." Anthropic ends unattended runs with a person approving the merge; GitHub forbids the agent from merging; Anthropic's engineers fully delegate 0-20%; the only "human optional" datapoint is OpenAI's secondary-sourced post in a repository engineered with structural linters for it; and Gas Town shows a PR merging "despite the integration tests failing." What makes orc's choice defensible is that its users cannot review a diff, so a diff gate would be theater; the honest replacement is a behavioral gate for the tickets where irreversibility lives. Auth, payments, data deletion and migrations, the domains orc already forces to L, should land in `needs-you` with a "try it" checklist before merge, and the done card should show the hard signals Anthropic's own success classifier uses: tests passed, diff summary, review findings.

**The lessons design is right in shape and wrong in its promise.** Three tiers, path scope, negative one-sentence rules, promotion on the second trigger, and enforcement as hooks map directly onto Anthropic's "corrected twice," "under 200 lines," "emphasis fails, then a hook" guidance, and METR's "patch the exploit." What the evidence contradicts is §7's "no human step is required for a lesson to start helping" as the sole safeguard: the MIT study shows a wrong recorded belief persists and degrades later runs, the ETH study shows overview-type context costs 20% for nothing, Replit shows compliance collapsing after three or four stacked reminders, Microsoft prescribes validation on every memory write, and Anthropic retired its own 2025 advice within a year because harness assumptions go stale per model generation. Lessons need provenance tags (verified, hypothesis, mistake), the model generation they were written against, expiry when untriggered, a validator that rejects anything that is not an instruction-shaped negative constraint, and a measured effect on review findings. An exploratory experiment also found that dozens of recorded past failures shifted a model toward caution on unrelated tasks without being flagged ([dev.to, fabricated memory, exploratory](https://dev.to/hammermei/does-bad-memory-make-ai-more-cautious-we-ran-the-experiment-2eoc)), which argues against injecting "Seen in T-014" narratives into worker prompts.

Three smaller contradictions. The fixed "up to three questions" should become conditional on scout confidence, as Devin does, because the model itself asks to clarify in only 13% of self-stops. The worker turn cap of 40 sits above the 20-25 that practitioners recommend "rather than retrying with more turns" ([apisrouter, practitioner](https://apisrouter.com/ci-coding-agent-budget-controls)) and Symphony's and AutoGen's default of 20; the evidence suggests 25 for S and M and a cap hit should write a handoff ledger and re-dispatch once in a fresh context before `needs-you`, not go straight there. And the "simplify" pass, which has no exact published counterpart, carries Anthropic's documented over-abstraction risk and should be constrained to deletions and reuse of existing code, never new abstraction.

## Conclusion

The loop orc describes is no longer a differentiator; by late 2026 it is the commodity shape every lab, three independent companies and the academic scaffolds have arrived at, and Anthropic has already shown which parts of it a better model makes redundant. What separates a strong framework from a fragile one is how little it trusts agent-authored signals and how well it measures its own components. Every serious failure in the record, from merged-with-failing-tests to 47 identical file reads to a false stacking belief that outlived the agent that wrote it, came from treating something an agent produced (a test, a "done," a lesson, a status) as ground truth. orc's security hooks already embody the right principle, "nothing is enforced by a sentence"; the work is to extend that principle to verification, state and memory.

The second implication is that orc should be built to shed parts. Anthropic dropped sprints and resets within four months of a model release; Cursor removed its judge and integrator; Amp removed compaction. `orc models suggest` is the right instinct applied to one knob. The same reopen-rate and review-finding telemetry should decide whether the reviewer, the questions step and each lesson tier are still earning their tokens on the current model, so that when the next generation makes the reviewer "unnecessary overhead" for M tickets, the data says so before the design does.

### Deliberately not adopting, and why

| # | Not adopting | Why |
|---|---|---|
| 24 | **Agent teams, peer messaging or any swarm inside a ticket** | Coding has "fewer truly parallelizable tasks" and multi-agent costs ~15x chat ([Multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)); teams cost "linearly" ([Agent teams](https://code.claude.com/docs/en/agent-teams)); swarms "mostly a distraction" ([Cognition](https://cognition.com/blog/multi-agents-working)); coordination needs 4x tokens and explicit design ([Multiagent systems](https://www.anthropic.com/research/multiagent-systems)) |
| 25 | **In-session LLM compaction for the worker** | Fresh process per stage already avoids it; LLM condensers cost +24-94% for no quality gain while masking saves ([arXiv 2605.18854](https://arxiv.org/abs/2605.18854); [Complexity Trap](https://arxiv.org/abs/2508.21433)); compaction "lossy" ([Amp](https://ampcode.com/news/handoff)); if ever needed, mask tool outputs instead |
| 26 | **Uncapped "loop until the critic is clean" fix loops** | Devin's autofix loop "massively increased" token spend ([Cognition](https://cognition.com/blog/closing-the-agent-loop-devin-autofixes-review-comments)); quality plateaued and "later iterations were not always better" ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)); an extra fixer agent introduced bugs ([Augment](https://www.augmentcode.com/blog/1-open-source-agent-on-swe-bench-verified-by-combining-claude-3-7-and-o1)). Two rounds then a fresh re-plan stays |
| 27 | **A universal human diff-review gate or PR-per-ticket by default** | The target user cannot review a diff, so the gate would be theater; the evidence for a human at the merge is a design rationale, not a measured outcome, and the only controlled human-in-the-loop study measures total time, not gates ([METR RCT](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). Replaced by row 11 (behavioral sign-off where irreversibility lives) and `merge: pr` as an option |
| 28 | **Different-vendor reviewer** | Not available inside a Claude Code plugin on a subscription; no controlled study shows a vendor effect; the proven lever is fresh context plus longer reasoning ([Best practices](https://code.claude.com/docs/en/best-practices); [arXiv 2504.03846](https://arxiv.org/abs/2504.03846v3)). Amp's and Replit's cross-model reviewers are experiential, not measured |
| 29 | **A third automated escalation tier (auto-Fable)** | Deeper cascades add ≤0.43 points in 118 of 135 comparisons ([arXiv 2605.06350](https://arxiv.org/abs/2605.06350)); orc's single Sonnet→Opus escalation on two check failures is the published shape |
| 30 | **Hidden tests written against an implementation** | Over-specific hidden tests reject correct work: 35.5% of hard SWE-bench Verified failures required a function name never mentioned ([OpenAI via Decrypt, secondary](https://decrypt.co/359012/openai-benchmark-measure-ai-coding-supremacy-contaminated)). Only spec-derived behavioral cases (row 21) are acceptable |
| 31 | **Model-judged security gates (`prompt`/`agent` hooks, "maybe irreversible" judges)** | "A `prompt` or `agent` hook asks another model to decide, so it isn't deterministic"; use command hooks with `onFailure: block` ([Best practices](https://code.claude.com/docs/en/best-practices)); Magentic-UI's LLM judge for "maybe irreversible" actions produced approvals users found "excessive" ([Magentic-UI](https://arxiv.org/abs/2507.22358)). orc's deterministic lists stay |
| 32 | **Repository overviews or architecture in CLAUDE.md or lessons** | "Claude reads the repo itself" ([Best practices](https://code.claude.com/docs/en/best-practices)); overviews are "not helpful" and cost 20% ([ETH](https://arxiv.org/abs/2602.11988)) |
| 33 | **Dollar budget as the primary stop** | No vendor caps by dollars; Symphony keeps tokens "for observability only" ([SPEC](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)); turn caps are the shipped control ([Best practices](https://code.claude.com/docs/en/best-practices)). Keep `--max-budget-usd` as the backstop |
| 34 | **Shared locks or a central integrator at Level 1** | Locks held too long cut throughput to "two or three" agents; the integrator "created more bottlenecks than it solved" ([Cursor](https://cursor.com/blog/scaling-agents)) |
| 35 | **Semantic search index for the scout; mutation testing by default** | "We suggest starting with agentic search" ([Agent SDK](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)); mutation-guided generation is production-proven at Meta (73% of tests accepted) but heavy, and many agent-written gates are vacuous, so it belongs on L-ticket gates that matter, later ([Meta ACH](https://arxiv.org/pdf/2501.12862)) |
